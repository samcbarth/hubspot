Your script created duplicate HubSpot records? Merge them, don't delete them

A bulk write through the API does not dedupe for you. When it goes wrong, the cleanup choice matters more than the bug.

Subscription
Any tier with a private app
Permissions
Private app with CRM write scopes
Time
15 min · Advanced
Validated
October 11, 2026, 5:20 PM ET

Short answer

The CRM API creates whatever you send. HubSpot's knowledge base says companies created through the API are not deduplicated by Company domain name, so a script that retries or runs twice creates duplicates. Merge the extra records into one primary record with the merge endpoint, then change the script to search before it creates.

1. How the duplicates happen

A script that runs in more than one phase, or retries after a timeout, can create the same company or contact again. Companies created through the API skip the domain check that imports and forms apply, so nothing stops the second copy. Imports dedupe differently. See import created duplicates for that side.

To merge two records by hand, open a record and use the Actions menu. Merge sits in the same menu as Opt out of email.

2. Merge from the script, not delete

For a large batch of duplicates, call the merge endpoint instead of merging by hand. The record ID in primaryObjectId stays. The record in objectIdToMerge is merged into it:

POST https://api.hubapi.com/crm/v3/objects/companies/merge
{
  "primaryObjectId": "PRIMARY_ID",
  "objectIdToMerge": "DUPLICATE_ID"
}

Contacts use the same body at /crm/v3/objects/contacts/merge. Keep the primary record's ID as the one you want to survive. Write the pairs to a file and review a sample before you run the merge.

3. Stop it recurring

  • Search before create. Query by domain (companies) or email (contacts) and create only when the search returns no match.
  • Upsert on a unique property. Where an object has a unique property, batch upsert with idProperty so existing records update instead of duplicating.
  • Make runs repeatable. Log the IDs your script creates, so a re-run reads them instead of creating the records again.
  • Compare totals after each batch. If the count is higher than expected, stop the run before the next batch.
